**Basically Unstoppable Saboteur Terrierizing Every Representation**

Buster is a chaos filter for HTTP servers. It sits in front of a server's
responses and tampers with them on purpose, then watches what the client does
next. Each plugin is both an attack and a test: it breaks a response one way,
and it says what a well-behaved client must do about it. It is named after a
Russell terrier who chews remotes, bites ankles, and jumps on everything.

Buster itself knows nothing about any one API. What it attacks is decided by
the plugins you load:

- **`plugins/`: the H.E.A.R.T. pack.** Buster was built to prove that ARTIE,
  the H.E.A.R.T. reference client, follows the 0.5 spec when the server
  misbehaves. These eight plugins each break one spec rule. For them, success
  means two things: every mutation ends in the failure path the spec names
  for it, and nothing corrupted is ever cached.
- **`samples/`: plugins for ordinary servers.** `flaky-503` turns a plain JSON
  API's successful responses into `503 Service Unavailable`, and checks that
  the client retries (see [A sample for any JSON API](#a-sample-for-any-json-api)).

Point `buster.plugins` at whichever folder fits the server under test, or at a
folder of your own.

## How Buster tampers with a server

Buster changes responses only. It never touches the server's stored state, so
turning Buster off returns the server to normal at once.

For every exchange, Buster does this:

1. **Watch the request.** Every inbound request goes to the verifier first.
   The verifier checks it against the open expectations for that client (see
   step 6).
2. **Let the server answer.** The real server handles the request as usual.
3. **Classify the response.** Buster decides what the response is from what a
   client can see: status, headers and body. The built-in classifier knows
   H.E.A.R.T.: it finds the layer (Layer 1 resource, Layer 2 affordance set,
   Layer 3 schema), the rung (L0, L1, L2) and the dialect (HAL Schema Forms or
   HAL-FORMS), taking the rung from `Preference-Applied`, never from what the
   client asked for. Anything it cannot place is `OTHER`: every response of a
   server that is not H.E.A.R.T., and error responses. Only plugins that name
   `OTHER` touch those.
4. **Pick a mutation.** From the plugins that apply to that layer and rung,
   Buster picks one, weighted by each plugin's `weight`. The choice comes from
   a random source seeded with the run's seed and the exchange's sequence
   number. The same seed against the same request sequence makes the same
   choices, so any failure can be replayed exactly.
5. **Mutate, then make it cache-safe.** The plugin changes the status,
   headers or body. Then the engine sets `Cache-Control: no-store`, whatever
   the plugin wrote. Otherwise a shared cache, such as the one in the
   H.E.A.R.T. two-client L3 demo, could keep corrupted bytes under an
   immutable URL for a year. A client may check what it receives; an
   intermediate cache does not. A plugin
   may keep its own `Cache-Control` only by calling `keepCacheControl()`, and
   only if the body bytes are unchanged. The engine checks the bytes, so a
   plugin author cannot get this wrong.
6. **Expect a reaction.** Each mutation declares what the client must do about it,
   and what its silence means. Buster judges that from the next requests the same
   client sends, and from the client's own event log. Every mutation ends as a
   `pass`, a `pass (attested)` or a `FAIL`; there is no fourth verdict. So every
   plugin is also a conformance test.
7. **Log everything.** Every mutation and every verdict goes to a JSON Lines
   log with its seed and sequence number.

```
client ──request──▶ [ verifier.observe ] ──▶ server
client ◀─response── [ classify ▶ pick ▶ mutate ▶ no-store ▶ expect ▶ log ] ◀── server
```

## Plugins are Kotlin scripts

A plugin is a Kotlin script named `*.buster.kts` in the plugins folder
(`buster.plugins`). There
is no build step and no jar. Buster compiles each script at startup with the
Kotlin scripting host. The Buster DSL is the script's implicit receiver, so a
script calls `plugin(...)` directly.

- Compiled scripts are cached by the hash of their source, so an unchanged
  script is not compiled twice.
- The folder can be reloaded while the server runs. A changed script is
  recompiled, a deleted script is dropped.
- A script that fails to compile is reported with its file name and the
  compiler's messages, then skipped. The other scripts still load.
- One script may declare several plugins.

### A plugin, start to finish

```kotlin
// plugins/strip-forms-integrity.buster.kts
plugin("strip-forms-integrity") {
    spec("§6.5")
    on(Layer.RESOURCE)
    rungs(Rung.L1, Rung.L2)

    mutate {
        val doc = json() ?: skip("body is not a JSON object")
        val link = Hal.link(doc, Hal.FORMS_REL) ?: skip("no forms link")
        val href = link.path("href").asText()
        link.remove("integrity")
        writeJson(doc)
        detail("removed integrity from the forms link $href")

        expect("refuse to follow a forms link without integrity", window = 5) {
            onRequest { req ->
                if (req.isGet && req.path == href) fail("followed $href") else pending()
            }
            onExpire { pass("never followed $href") }
        }
    }
}
```

### The DSL

At the top level of a script:

| Call | Meaning |
| - | - |
| `plugin(name) { ... }` | Declares one plugin. |

Inside `plugin { ... }`:

| Call | Meaning |
| - | - |
| `spec("§6.2", ...)` | The spec sections or RFCs the plugin attacks. Logged with each mutation. |
| `on(Layer.RESOURCE, ...)` | The layers it applies to. Required. `Layer.OTHER` is any response that is not H.E.A.R.T. |
| `rungs(Rung.L1, ...)` | The rungs it applies to. Default: every rung. |
| `weight(n)` | Relative chance of being picked. Default 1. |
| `mutate { ... }` | What the plugin does to a response. Required. |

Inside `mutate { ... }`:

| Call | Meaning |
| - | - |
| `request`, `response`, `classification` | The exchange. The request is read-only. |
| `random` | The seeded random source for this exchange. Use only this, so replay works. |
| `resourcePath` | The path of the resource this response is the state of: `Content-Location` (RFC 9110 §8.7), else the HAL self link, else the request path. An act answers at its action URL, so it is the resource, not `request.path`, that a later read is of. |
| `future` | What this client sent after this request in the dry run (see [Campaigns](#campaigns-aiming-each-mutation)), or `null` with no dry run. Skip when the client never exercises the rule. |
| `json()` / `writeJson(node)` | Read the body as a JSON object, write it back. |
| `detail(text)` | What was changed, for the log. |
| `skip(reason)` | Leave the response alone. The skip is logged. |
| `keepCacheControl()` | Ask to keep the plugin's `Cache-Control`. Honoured only if the body is unchanged. |
| `expect(description, window) { ... }` | What the client must do next. |

Inside `expect { ... }`:

| Call | Meaning |
| - | - |
| `trigger` | The request whose response was mutated, so a plugin can judge the read that got the mutation. |
| `onRequest { req -> outcome }` | Runs on each later request from the same client. |
| `onEvent { event -> outcome }` | Runs on each line of the same client's event log. It can only `attest(reason)` a pass. |
| `onExpire { decided }` | Required. What silence means: the client is done, or the round ended, and nothing settled it. It can only return `pass(reason)` or `fail(reason)`. |
| `pass(reason)`, `fail(reason)`, `attest(reason)`, `pending()` | The outcomes. `pending()` is for `onRequest` and `onEvent` only. |

An expectation without `onExpire` is refused, and `onExpire { pending() }` does
not compile. A check that could not be judged cannot be written, so a plugin
has to decide what its silence means: for some rules a client that never
exercises them has nothing to answer for (a pass); for others, never making
the act the rule is about is the failure. Closing a window always runs that
rule, even for a client that sent no request after the mutation.

## Campaigns: aiming each mutation

A mutation is only worth making where the client will exercise the rule it
attacks. Mutate a response the client never uses and nobody can say what
should have happened. A campaign aims each mutation from a dry run:

1. **Record.** `POST /_buster/campaign/record`, then run the client's
   scenarios once against the unmutated server. Buster keeps every client's
   requests and responses, by the client's label (its `User-Agent`, which is
   stable across runs; trace ids are not) and the request's position.
2. **Plan.** `GET /_buster/campaign/plan` runs each plugin over each recorded
   response in plan mode, with that client's later requests as `future`. A
   plugin that does not apply calls `skip()`, and the plan says why. What is
   left are combinations (client, request, plugin), grouped into rounds:
   round k holds the k-th combination of each client, so one run mutates at
   most one exchange of each client while their scenarios go on side by side.
3. **Arm.** For each round: reset the server, `POST /_buster/campaign/arm?round=k`,
   and run the same scenarios again. Only the armed exchanges are mutated,
   matched by label and position. Unarmed clients, such as a readiness probe,
   and unplanned requests pass through untouched. A window stays open until the
   client sends `client.done` or the next round is armed.
4. **Read the gate.** `GET /_buster/report?flush=true` carries a `campaign`
   section: the combinations each plugin was planned and actually made, the
   plugins that got none, a plugin by client matrix of verdicts, any
   misaligned combination, and `ok`. A campaign fails on any FAIL, on any
   plugin with no combination made (a coverage hole: no scenario exercises that
   rule, and it needs a new one), and on any **misaligned** combination: one a
   round armed and did not make, because the plugin skipped it at run time or no
   request came at that position. The client did not do in the run what it did
   in the dry run, so that round proves nothing. It is reported with the client,
   the position, the plugin, the planned path and the live path (or "no
   request"), and is never silent.

Two things keep a run honest about what it judges:

- **Clients that interact are not armed together.** Clients that overlap in
  time and touch a common resource, with at least one write, are a group in the
  plan, and a round arms at most one of them. Two clients of one scenario
  acting on one bed would otherwise end each other's scenario. The groups come
  from the dry run, not from anything in a client's name.
- **A fresh representation replaces the mutated one.** Buster sends `no-store`
  with a mutation, so the client keeps nothing of it. When the client enters the
  resource again and is answered a whole, unmutated representation, the window on
  the mutated one closes (`onSuperseded`): what the client does with the fresh
  one is its own business.

`POST /_buster/campaign/off` returns to mutating by seed. With a plan in hand,
the seed samples from the plan's combinations rather than from every response.

Which dry-run requests arm each plugin:

| Plugin | Armed where the client goes on to | Silence is |
| - | - | - |
| `relax-layer1-cache` | (a read: always, judged on that read. An act's response: only where the client reads the resource again) | pass if the read that got the response said `no-cache` (an act is a write, so it has none to judge), else FAIL |
| `drop-affordance` | act on an affordance of the resource: that one is dropped | pass; attested by `affordance.absent` |
| `stale-etag` | act with `If-Match` equal to this ETag | FAIL: the act never came |
| `alias-forms-href` | GET the forms link | FAIL: never followed it |
| `strip-forms-integrity`, `drop-curie`, `lie-preference-applied` | follow the forms link | pass; attested by the client's event |
| `flip-byte` | act using that set or schema | pass: never used the corrupted bytes |

## A sample for any JSON API

Nothing about Buster needs H.E.A.R.T. This sample, in `samples/`, plays an
overloaded server in front of an ordinary JSON API:

```kotlin
// samples/flaky-503.buster.kts
plugin("flaky-503") {
    spec("RFC 9110 §15.6.4")
    on(Layer.OTHER)

    mutate {
        if (response.status !in 200..299) skip("only a success can turn flaky")
        if ("json" !in response.headers["Content-Type"].orEmpty()) skip("not JSON")
        val method = request.method
        val path = request.path
        // Silence is a FAIL here, so only where the dry run shows the client going on to use this
        // resource: there is then something it must not do after a 503.
        val seen = future ?: skip("no dry run, so silence would be a guess")
        if (seen.none { it.path == path }) skip("the client never goes on to use $path in its dry run")
        response.status = 503
        response.headers["Content-Type"] = "application/problem+json"
        response.headers["Retry-After"] = "1"
        response.body = """{"status":503,"title":"Service Unavailable"}""".toByteArray()
        detail("$method $path answered 503, Retry-After 1")

        expect("retry $path rather than change it unread", window = 3) {
            onRequest { req ->
                when {
                    req.method == method && req.path == path -> pass("retried $method $path")
                    req.isAct && req.path == path -> fail("${req.method} $path without reading it first")
                    else -> pending()
                }
            }
            onExpire { fail("never retried $path") }
        }
    }
}
```

| A client that | Verdict |
| - | - |
| retries the same request | pass |
| changes the resource it never managed to read, such as `DELETE /todos/1` | FAIL |
| moves on to something else | FAIL |

Run it with `buster.plugins=samples`. A plain JSON API without ETags is all
`OTHER` to the classifier, so this plugin can reach every successful JSON
response.

## The H.E.A.R.T. pack

The pack is the scripts in `plugins/`. Each one, what it does, and how Buster
judges the client from its next requests:

| Plugin | Mutation | Passes when the client | Fails when the client | Spec |
| - | - | - | - | - |
| `stale-etag` | Forges the Layer 1 ETag | revalidates before acting, or gets 412 and re-syncs | resubmits the act with the stale ETag | §6.2, §6.3 |
| `drop-affordance` | Drops one embedded affordance from an L0 manifest | never acts on it | acts on its method and target | §6.2 |
| `flip-byte` | Changes one letter inside a JSON string in an affordance set or schema | refetches the same URL before acting; attested by `integrity.refused` | acts before refetching | §6.5 |
| `strip-forms-integrity` | Removes `integrity` from the forms link | never follows the link; attested by `integrity.refused` for it | follows it | §6.5 |
| `lie-preference-applied` | Removes `Preference-Applied` from an L1 or L2 response | treats it as L0 with no affordances; attested by `forms.skipped` | follows the forms link, or acts before reading the resource again | §6.11.1, §6.4 |
| `drop-curie` | Removes `_links.curies`, so `hr:forms` no longer expands | never follows `hr:forms`; attested by `forms.missing` | follows it | §6.1, §7.5 |
| `alias-forms-href` | Adds a query the server did not write to the forms link | follows the link as given | requests the bare path, building the URL itself | §6.5 |
| `relax-layer1-cache` | Sets Layer 1 to `private, max-age=3600` | reads the resource again with the request directive `Cache-Control: no-cache` | reads it again without that directive | §6.3 |

Silence is decisive in every plugin. A client that never exercises a rule
passes the plugins that attack a link it was never going to follow, and fails
`stale-etag` and `alias-forms-href`, whose whole point is the act or the
follow: they are made only where the dry run shows the client doing it.

### The client's event log

Some right behaviour sends nothing: a link not followed, tampered bytes
refused. A client can say what it decided in an event log: one JSON line per
decision, in OpenTelemetry log data model fields (`trace_id`, `span_id`,
`event_name`, `attributes`). ARTIE writes one when `ARTIE_EVENTS` (a file) or
`ARTIE_EVENTS_URL` (a URL) is set. Buster reads it two ways: it follows the
file named by `buster.client-events`, and it accepts lines POSTed to
`/_buster/events`.

Each event names the client by trace id and the request it is about by span
id, from the W3C `traceparent` the client sent. An event can only attest a
pass, shown as `pass (attested)`, which the report keeps apart from a pass
seen on the wire. A failure comes only from the wire, and nothing a client
says can clear one. `client.done` closes that client's open windows with
their own expiry rule, so a client that stops at the end of a scenario is
judged by what its silence means for each rule.

Some judgements are approximations, and the scripts say so:

- "Never cache it" cannot be seen from requests. `flip-byte` judges the
  observable part: the client fetched those bytes because it needed them, so
  acting before it refetches means it used the corrupted copy.
- `relax-layer1-cache` does not judge the act made straight after the read:
  that read was the fresh check, and `If-Match` guards the act. It judges the
  read that got the mutated response instead: `no-cache` on that read is the
  pass, and its absence is a FAIL. A later read that the client's own cache
  answers never reaches Buster, so it is not judged.
- No plugin reads meaning from a URL. A request is tied to a resource only by
  equal paths, and an event to a request only by trace and span.
- `alias-forms-href` relies on the server ignoring query parameters it does
  not know, so the aliased URL serves the same bytes.

RISE is out of scope while it is on hold.

## Safety

Plugin scripts run in-process with full JVM power. This is not a sandbox.
Buster is for development only, with scripts you trust:

- One global switch turns Buster on, tied to a server profile, so it cannot
  run in production by accident.
- The core package imports no server framework. An architecture test enforces
  this, so the same engine can sit behind any HTTP adapter.

## Running Buster in a Spring WebFlux server

Buster ships a `WebFilter` and a Spring Boot auto-configuration. The filter
runs at `Ordered.HIGHEST_PRECEDENCE`, so no endpoint can opt out. It buffers
each response body, hands it to the engine, and writes the result back with a
correct `Content-Length`.

The `buster` profile is the one switch: without it none of Buster's beans
exist. Spring is `compileOnly`, so Buster uses the host server's Spring.
Under the profile, Spring prints Buster's terrier in place of its own banner,
so the console shows at a glance that responses are being tampered with. A
server that sets its own `spring.banner.location` keeps it.

In ARTIE's `server-spring`, Buster is opt-in. Only `-Pbuster=on` brings it
in, through a composite build of `../buster`, as a `developmentOnly`
dependency. Without the flag the server's build never sees Buster. Spring
Boot leaves `developmentOnly` out of the boot jar, so a production build
carries no Buster code at all.

```
cd ../server-spring
SPRING_PROFILES_ACTIVE=buster BUSTER_SEED=42 ./gradlew bootRun -Pbuster=on
```

Two switches, both needed: `-Pbuster=on` puts Buster on the classpath, and
the `buster` profile turns it on.

| Property | Meaning | Default |
| - | - | - |
| `buster.plugins` | The folder of `*.buster.kts` scripts | `plugins` (`../buster/plugins` in server-spring) |
| `buster.seed` | The run's seed. Unset means a random one, logged for replay. | random |
| `buster.log` | A file for the JSON Lines log | in memory only |
| `buster.client-header` | The header that labels the client, and names it when it sends no `traceparent` | `User-Agent` |
| `buster.client-events` | A client event log (JSON Lines) to follow as it grows | none |
| `buster.pace` | Slow motion: how long to hold each mutated response, such as `2s`. Responses Buster leaves alone are never held. | `0s` |

Buster judges each mutation from the same client's next requests, so it must
tell clients apart. It does that by the trace id of the W3C `traceparent`
header, which exists to group one client's requests, and labels the client by
`User-Agent` in the report. A client that sends no `traceparent` is told apart
by `User-Agent`, so give each its own, such as
`ARTIE/0.5 (two-clients; second)`; without either, Buster falls back to the
remote address, and every client on one machine counts as one.

### Watching a run

Open `/_buster` in a browser for the live view. It is a small htmx page:
every second it asks `/_buster/report` for HTML, and the server renders one
row per mutation, newest first, with its verdicts as they land. 🐕 marks
what Buster did; the verdict column is what the client did about it. **End run**
closes every open expectation. With `buster.pace` set, the mutations arrive
one at a time, slow enough to follow.

`GET /_buster/report` returns the seed, the pace, the mutations and the
verdicts so far as JSON. `?flush=true` ends the run first. A request with
`HX-Request: true` gets the HTML rows instead.
